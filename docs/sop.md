# worker 操作细则

> worker 每接一单都按本文执行。浏览器工具的具体 API（维护者用 ego-browser 的 TaskSpace、`handOff()`、`takeOverTaskSpace()`）以工具自己的文档为准，本文只写与工具无关的步骤和规矩。
> 开工前必读：本文、`docs/redlines.md`、实例 `profile.md`、`question-bank.md`、`accounts.md`、对应 `portals/*.md`。

## 0. 铁律

1. 只用分给自己的那一个浏览器空间。第 1 页固定看板，门户开在后续页。
2. 任务闭环（已投递并核验、或已判不合适）后关闭浏览器空间；在跑或等用户的空间不关，也不开新的。
3. 写操作前重新定位目标：公司名、公告标题、届数三要素全部核对。
4. 禁止按视觉行号或“第 N 行”操作，表格行序随时会变。
5. 所有写入以刷新后的回读为准，不信即时回显。
6. 需要用户动手时：先预填所有能填的字段，再调用 `host/notify.py handoff`，然后交还浏览器并停手。

## 1. 单家公司骨架

1. **收工单**：公司、announcement_id、链接、届数原文、方向线索、提交档位（worker / user）、截止日。
2. **打开空间**：第 1 页打开看板。
3. **定位**：在本机公告数据（`data/paperball/announcements.jsonl`）里按公司名查，用 announcement_id 对齐；0 条或多条无法消歧 → blocked。
4. **防重**：查 tracker、你自己的看板（若有）、门户申请记录（登录后）。同雇主主体有记录 → blocked。
5. **届数预筛**：`class_types` 不含 `intent.class_types` → 看板标不合适，备注原因，回执结束。
6. **岗位详查**：打开投递链接或公告原文，逐个读候选岗位 JD，按 `intent.roles` 选最合适的一个，记下备选。核实门户实际截止日（门户与看板不一致时以门户为准）。
7. **判定投递方式**：邮件 / 官网表单 / 需注册，见 §3。
8. **执行**：见 §3、§4。
9. **提交或停手**：按工单档位，见 `docs/redlines.md` §1。
10. **核验**：门户“我的投递”回读，截图。
11. **回写进度**：写 outcome（`host/events.py outcome`）；你另有自己的看板时再同步过去。
12. **留痕 + 回执**：见 §6、§7。

## 2. 阶段定义

| 阶段 | 内容 | 结束动作 |
|---|---|---|
| 阶段 1 | 查岗，打开到登录/注册墙 | 预填字段 → handoff → 停手，不回执 done |
| 阶段 2 | 用户处理完后接管，填表到提交前 | worker 档：提交；user 档：截图 → handoff → 停手 |
| 阶段 3 | 提交后核验门户状态 | 看板标已投递 → 留痕补记 → 回执 |

阶段 1 结束时给主持人发一条 team-msg，说明在等用户做什么。用户处理期间不关空间、不开新空间、不动该空间任何页面。

## 3. 投递方式

### 3.1 邮件

- 看板投递链接含 `@` 时，只收集要素，不做任何发送动作。
- 要素写入实例 `log/email-queue.md`，一行一岗：
  `公司 | announcement_id | 岗位名 | 收件邮箱 | 附件命名格式 | 邮件主题格式 | 正文要求 | 公告链接 | 状态`
- 优先抄公告原文的要求；公告没写的字段标“公告未注明”。
- 看板标待投递，备注“邮件投递，要素已入队”。
- 起草按 `templates/mail/cover-letter.skeleton.md`，发送受 `intent.permissions.email` 约束。

### 3.2 官网表单

- 先识别入口：注册墙 / 扫码 / 验证码 / 直接表单。
- 有账号体系的，登录后先查申请记录再填表。
- 门户识别方式与坑见 `portals/`。

### 3.3 需要注册或登录

**登录通道优先级**（项目约定，完整判定流程与各平台默认通道见 `docs/auth-channels.md`）：
平台预登录（accounts.md 命中）→ 邮箱码（himalaya 自取）→ 手机短信码（`host/sms-code.py` 自取）→ 扫码 handoff。能用上游就不用下游。

1. 查 `accounts.md`，命中已知门户就按记录的方式走。
2. 按 `intent.permissions.register_accounts`：
   - `user`：预填后 handoff，用户完成注册。
   - `worker_email_only`：只允许邮箱 + 邮件验证码注册；验证码用 himalaya 自取。发码前出现图形验证码，先走图形码支线（验证码特种兵），连败再 handoff。
3. 预填：手机号、邮箱、姓名、证件号、密码（按问题库 `account` 类答案）、可勾的协议框，全部填好，停在只剩验证码和最后一下点击的状态。
4. 验证码自取：
   - 邮箱码：himalaya 读收件箱自取；TTL 太短（约 1–3 分钟）、取码加提交往返两次仍超时，改走手机码或用户手输。
   - 短信码：`uv run $CAMPUS_REPO/host/sms-code.py --since 5m --sender-hint <公司或平台名> --wait 90`；取到填入继续，退出码非 0 再 handoff（kind=sms_code）。
   - 短信码自取只用于登录已有账号；新注册仍按 `register_accounts`。
5. 登录的是已有历史账号时，先回读账号存量：旧简历附件、历史投递、已填字段。旧附件换成当前简历并刷新回读；存量字段与问题库冲突的，以问题库为准；发现历史投递 → 防重，报主持人。
6. 新账号注册成功后，把门户、登录方式、账号写进实例 `accounts.md`。

## 4. 填表

### 4.1 字段来源

`profile.md` → `question-bank.md` → 简历 PDF → blocked。字段名对不上时查问题库的 `aliases`。

### 4.2 通用规则

- 按具体问法判断声明类题目：问“是否有不良记录”答否，问“是否无不良记录”答是。拿不准的措辞 blocked。
- 选项类默认规则（到岗时间、排名档位、专业库映射、城市多选顺序等）以问题库 `rules` 为准。
- 表单没有“实习经历”栏但有“项目经历”栏时，把实习写进项目经历。
- 字段长度限制、特殊字符限制（常见禁止 `# $ / < >`）会导致保存静默失败，写长文本前先看限制。
- 在职或进行中的经历，控件没有“至今”时选当前月，并在留痕注明。
- 简历解析结果要逐字段对照简历原文修正：项目名丢前缀、两段描述并到一条、日期错位、手机号填进证件号都出现过。

### 4.3 附件

- 中文站传中文简历 PDF，外企按 `intent.policies.foreign_cv`。HTML 版简历不能当附件。
- 证件照、生活照、其他材料取自实例 `materials/`，规格和压缩见 `docs/materials.md`。
- 上传后：截图 → **刷新页面或退出编辑态重进** → 回读文件名。只信刷新后的结果。
- 有的门户上传照片后要再点所在区块的“保存”才落库。
- 附件路径写错时，部分组件仍会回显文件名但不发请求。

### 4.4 保存与刷新

- 有“暂存”的表单，刷新或离开前先暂存，否则丢数据。
- 长表单分段保存的，每段保存后刷新回读一次。
- 同一时刻只允许一个区块在编辑态的表单，提交前确认没有区块停在编辑态。

## 5. 并发与冲突

- 看板的筛选、排序是页内状态，多个空间互不影响；弹层只挡本页。
- 同一门户账号不要在多个空间并发登录，同一批次尽量分散到不同 ATS。
- 写看板前重新搜索定位，写完用 announcement_id 回读。

## 6. 操作留痕（强制）

每单写 `$CAMPUS_INSTANCE/log/ops/<批次>-<announcement_id>.md`，让任何 agent 事后能接手：

```markdown
# 操作留痕 · <批次>-<id> <公司>（<门户类型>）

## 门户与账号
- 投递站 URL、岗位详情最终 URL、申请表 URL
- 登录方式（邮箱 / 手机码 / 扫码 / 免登录），不写账号明文和密码
- 投递限额（如“最多投 3 个岗位”）、门户截止日

## 逐步操作
1. 点了什么（按钮文本或选择器）
2. 填了哪些字段（字段名 = 来源：profile / 问题库 / 简历）
3. 上传了什么（materials/ 下的文件名），刷新回读结果

## 停在哪一步
- 最后页面状态、提交按钮的文本和位置、截图路径、TaskSpace 编号

## 后续核查方式
- 登录后去哪看投递状态（菜单或 URL）

## 卡住点与绕过
- 弹窗、验证码、控件怪癖及处理
```

之后每个阶段在末尾追加一节，不改前面的内容。

## 7. 回执格式

```
公司 | announcement_id | 公告标题 | 届数原文
判定：合适（岗位名 + 投递方式）/ 不合适（原因）
执行：停在第几步 / 已完成哪几步 / 提交证据
进度回写：outcome 已写 | 备注原文
证据：截图路径 | TaskSpace 编号
阻塞：需要用户做什么；门户实际截止日；投递后测评期限
```

回执写入 `~/.seedmux/team/tasks/<task>/reply.md`，首行一句结论，然后 `smx-team reply <task> --status done|blocked|failed`。

## 8. 失败边界

| 情况 | 处理 |
|---|---|
| 掉登录 | 按 §3.3 通道优先级恢复（accounts.md 记录的方式；邮箱码/短信码可自取）；只剩扫码或自取失败 → handoff |
| 图形验证码、扫码、人脸 | 图形码先验证码特种兵（连败 3 次）再 handoff；扫码、人脸直接 handoff，见 redlines §2 |
| 短信验证码 | 先 `host/sms-code.py --wait 90` 自取；退出码非 0 → handoff（kind=sms_code） |
| 投递链接失效 | 改走公告链接；都失效且岗位合适 → blocked；确认已截止 → 不合适，备注“已截止” |
| 方向模糊（产品/运营/纯研究等与 intent 不明确对应） | blocked 问主持人 |
| 必填字段无数据源 | blocked，列出字段名，不编 |
| 申请已成功但看板回写失败 | 不重投，blocked 说明 |
| 超时、异常、页面卡死 | 先查留痕和门户记录，禁止盲重试；页面被 alert 风暴卡死可开新页恢复，登录态通常保留 |
| 点击后无反应 | 先看是否弹出了验证码遮罩或确认框，再判断 |

## 附录：看板进度回写

公开版不带任何第三方看板的接口说明。投递进度以实例 `tracker.md` 与 `state/outcomes/` 为准；要回写到你自己用的看板，自行实现。

## 工具速查（ego-browser，踩过的坑）

- 上传文件的方法名是 `setInputFiles`（不是 setFileInput）；页面有多个隐藏 file input 时先定位到简历区块内的那个再传
- 长时间等待（等关卡、等邮件码）不要写成一次跑几十分钟的脚本：**每轮最多 2–3 分钟就结束命令回到对话**，否则主持人发来的消息会一直排队读不到
